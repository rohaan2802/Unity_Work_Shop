Movement and input

Both original scripts are CharacterController.cs and NewMonoBehaviourScript.cs. The first uses +=. The second assigns the position back. The class names differ. The bug does not.

The test that is always true

Input.GetAxis for Horizontal and Vertical returns a value from about -1 to 1 when the keys in InputManager.asset are used. Horizontal is A and D, and the arrow keys left and right. Vertical is W and S, and up and down. A value in that range is always greater than -2. The if in the workshop script therefore does not reject input. The script moves on every frame by whatever the axis currently is, including zero, which adds nothing.

The new Walker does not use that comparison. It uses the axis as a direction, clamps the diagonal so speed stays at 5, and calls CharacterController.Move.

The root script's class is named CharacterController. That is the same simple name as UnityEngine.CharacterController. Inside Assets it would hide the engine component. Both originals stay outside Assets. The component that runs in Courtyard Walk is Walker.

In vrscene the asset script is attached to the Ely instance and saved disabled. The GUID is 8da2fb2bc5e016b46a58a9a76e50a30f. See workshop-evidence.

The workshop Player Settings used Active Input Handling = Both, because Starter Assets uses the Input System package while the handwritten script uses the legacy axes. This project sets Active Input Handling to the Input Manager (activeInputHandler: 0). If that setting is changed to Input System Package only, GetAxis will not see the keys.
